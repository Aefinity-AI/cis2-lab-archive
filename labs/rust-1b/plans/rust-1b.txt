QUESTION. On the same small model and the same 64 teacher-forced tokens on an old laptop CPU, how do a Rust program calling a library kernel, PyTorch and llama.cpp compare (framework), how do our own Rust kernels compare with the library kernels inside torch (kernels), and how much memory does each use?

BIGGER SYSTEMS NAMED. The established stacks to beat or match are PyTorch 2.14.0+cpu in fp32 with MKL (arm T) and llama.cpp F32 (arm Q). The expected outcome is that our Rust arms are behind them (see EXPECTED VALUES); a result that is level or ahead is a SURPRISE and is flagged as such.

TRUST COLUMN, REPORTED NEXT TO EVERY SPEED LINE. See the TRUST COLUMN paragraph below: hash behaviour of T, dependency count per arm, lines of the decode loop per arm, and for G-OB the largest logit difference to L-C. Every arm is named pure Rust or not pure Rust.

WHAT IS COMPARED (all on SmolLM2-135M, one weights file per format, sha256 recorded before the initial timing run).
 G-OB Rust glue + OpenBLAS: the cis2_ref decode loop with each matrix-vector product replaced by cblas_sgemv (openblas-src, system OpenBLAS, version and core type recorded, OPENBLAS_NUM_THREADS=1). NOT pure Rust (links a C/Fortran library). Arithmetic differs from L-R and L-C (vectorised across k, may fuse), so no digest is required; the largest logit difference to L-C on the 64 positions is reported.
 G-MKL (optional) Rust glue + MKL: same, calling cblas_sgemv from libmkl_rt (pip "mkl" wheel, version recorded, MKL_VERBOSE output kept). NOT pure Rust. If G-MKL is absent, the FRAMEWORK sentence says "Rust glue + OpenBLAS versus PyTorch + MKL: kernels differ, so this is stack against stack, not glue alone". G-MKL is required for any FRAMEWORK sentence that claims "glue alone"; without G-MKL that wording is not written. G-OB is the required arm; G-MKL is optional.
 T    PyTorch: torch 2.14.0+cpu wheel (the wheel used in cap-1b), fp32, manual forward loop with KV cache fed the fixed token ids (no generate()), torch.inference_mode(), no torch.compile, attention implementation sdpa, torch.set_num_threads(N), torch.set_num_interop_threads(1), OMP_NUM_THREADS=N, MKL_NUM_THREADS=N; torch.__config__.show() output (MKL or OpenBLAS state) and MKL_VERBOSE kept; on the N4020 hosts the dispatch line is recorded. transformers version copied from SV5B and written in the result. NOT pure Rust (Python plus C++ plus MKL).
 Q    llama.cpp: one commit pinned (b11381 or newer, hash recorded), built with the host's own flags, F32 GGUF made from the same safetensors, one-token-at-a-time decode over the fixed ids through the llama.cpp API (a small C++ driver), -ngl 0, threads N. Q8_0 GGUF is an extra row, labelled "different arithmetic". NOT pure Rust (C/C++).
 X    (optional) Rust-fast: a Rust engine with AVX2 kernels and scalar fallback on the same architecture. Counts only if built and verified by 2026-10-08. If it is not built the result reads "engine: NOT TESTED" and no verdict of any kind is written for it.
 Extra, reported only, no label: Candle CPU (NOT pure Rust: default matmul is the Rust gemm crate, optional MKL off, version recorded).
 Not run, known: torch on box4 and box5 ("Illegal instruction" on import, R/2026-10-01-SW0-CPU-TRAIN-THROUGHPUT.md). 360M is not in this bar (verify3 stops on non-pinned weights and no digest reference exists); a 360M extension needs its own bar written beforehand.

 ARM L NUMBERS. The Rust CIS-2 implementation (L-R, cis2_ref) and the C CIS-2 implementation (L-C, verify3 / sv5_driver) are measured by rust-1, not here. rust-1b does not re-measure arm L. Its FRAMEWORK memory line takes the L-R and L-C peak PSS rows from rust-1 (verified, recorded jobs) and says that they were taken earlier, on a different day and job; no speed pair of this bar contains an arm L build, and no row of rust-1 enters a Band W ratio. SAME WORK. Prompts: the leading 8 of the sv-5 prompt set (file path and sha256 recorded at build). The 64 token ids per prompt are the greedy output of L-C, produced once, stored with sha256, with no EOS stop (these are the ids of the rust-1 freeze, file ids64.jsonl, sha256 e939542aa2b2112822e36c7564817ddc61ddad8d513c9a49dd3f8a4d46d60955, reused and not regenerated; the leading 8 prompts are the 8 lines with sha256 1e6a0046d7c39661bb625a492c0d943d1cd829e786bdbcf4f5c840bc43c3e826). Every arm decodes exactly those ids (teacher-forced), so sequence lengths are equal by construction. One extra warm-up prompt is run beforehand and discarded. Weights: L-R and L-C read the bf16 file and widen to fp32 (the pinned format); T, Q and G read the fp32 conversion of the same bf16 values (identical numbers, different load path; stated in the result).

FIXED SETTINGS TO RECORD (and freeze before the initial timing). Rust: rustc version, RUSTFLAGS, opt-level, lto fat, codegen-units 1, panic abort, target x86-64 baseline gnu (a musl static build is a separate extra, reported only, and is the only form built for box4 and box5), global allocator, whether rayon is linked and the pool size (1 at N=1, checked by Threads). C: gcc version, -O2 and -O3 each built, -mno-fma -ffp-contract=off, no -ffast-math; clang as an extra. Per host the "C reference" is the faster of the two C builds and the "Rust reference" is the faster of Rust opt-level 2 and 3 (rule fixed now, applied mechanically to the medians). Both languages get the same effort: neither source is tuned after the initial timing run. For rust-1b the rule of the faster of two opt-levels is applied to every Rust arm (G-OB, G-MKL, X): both opt-levels 2 and 3 are built and the faster one per host, by the median of its reps, is the reference of that arm (stricter reading of a rule the registered text states for L-R and L-C; the C sentences of this paragraph describe arm L and are carried for the record).

METRIC AND STATISTIC. Timing is the in-process wall of decode steps 2 to 64 (63 steps) per prompt. Per-rep value = (8 x 63 tokens) divided by the sum of the 8 prompt walls, in tokens per second. Statistic = median of 5 per-rep values per arm per host (10 when a label is INCONCLUSIVE, once). Threads N=1 for every label; N=2 on box1 and box2 is reported with no label. Memory: peak PSS and peak anonymous bytes sampled every 50 ms from /proc/<pid>/smaps_rollup over the whole process, plus VmHWM; the values used are the medians of the 5 per-rep peaks of PSS and of anonymous bytes. The Rust safetensors crate maps the weights file (mmap) and the C loader read()s it, so PSS carries an I/O-method effect; the result states the load method of each arm. Reported with no label: prefill tokens per second, load time, time from process start to the opening generated token with warm page cache (cold cache belongs to rust-4). (rust-1 found that cis2_ref reads the weights with std::fs::read into a heap buffer and does not map the file; the rust-1b result states the load method of each arm as its own code does it, and does not rely on the sentence about the safetensors crate.)

HYGIENE. Host idle (uptime load average below 0.3 and fx status clear before and after, else the rep is void); no CPUQuota; every job under systemd-run --user with MemoryMax box1 4.5 GB, box2 and box3 2.8 GB, box4 and box5 80 percent of the free -m total (a job killed by the limit is recorded as OOM, not dropped); CPU MHz from /proc/cpuinfo before and after each rep, a rep with more than 15 percent drop is discarded and repeated (three discards on one host make that host INVALID); arm order rotated each rep; thread count checked from /proc/<pid>/status. penguin is never used for timing.
