# E22 — CIS-2.5: bf16-weight / fp32-accumulate inference, a design memo

**Date:** 2026-09-03 · **Status:** design memo, not a spec, not normative, HELD (no publish decision made). **Rule A:** no timing/throughput/speed claim appears below. **Rule B:** every number below cites the command/file/commit that produced it, or is marked as a plan (not yet run).

**Purpose.** CIS-2 v0.2 (`~/projects/cis2-fp/docs/CIS2_SPEC_v0.2.md`, private) already stores weights as bf16 on disk and widens them losslessly to fp32 before any arithmetic (§4, verbatim below). That is a narrower claim than what "bf16 inference" means to the two nearest publications: Microsoft's RepDL (arXiv:2510.09180) names bf16/fp16 as its explicit next goal, blocked today on "non-standard GPU low-precision arithmetic"; arXiv:2606.00279 already ships a CPU emulator that reproduces real GPU BF16 inference bit-for-bit, but only by cloning one specific vendor's specific kernel's rounding behavior, not by conforming to a portable spec. Neither has a bf16 **contract** — a written definition of where bf16 rounding happens, what "reference" means for a lossy format, and what a second, independent implementation would need in order to reproduce the same bits. This memo proposes one, scoped to what CIS-2's existing fp32 engine can absorb cheaply and honestly.

---

## 1. The contract

**Claim shape:** bf16-weight, bf16-activation-at-layer-boundaries inference, fp32 internal accumulate, reproducing one pinned digest bit-for-bit across independently-compiled x86-64 and aarch64 implementations, from a written spec text alone — the same claim shape CIS-2 v0.2 already proved for the narrower "bf16-storage-only" case (§3 below cites the exact clean-room evidence).

### 1.1 Where bf16 lives

Two designs are possible; this memo picks the first and states why.

- **(a) Weights only (what CIS-2 v0.2 already does).** Every tensor is bf16 on disk, widened once at load via the exact, lossless bit-shift `f32_bits = (b as u32) << 16` (CIS2_SPEC_v0.2 §4.1) — not a rounding conversion, because bf16's sign/exponent/mantissa layout is fp32's top 16 bits with the low 16 mantissa bits zero. All compute — matmul, RMSNorm, attention, RoPE, transcendentals — runs in the existing pinned fp32 engine (§5–§8 of the same spec). Activations are never bf16.
- **(b) Weights and activations at layer boundaries.** Same weight widening as (a), plus: after each major op (attention output, MLP output, residual add, or per §1.2's chosen granularity) the fp32 activation tensor is rounded to bf16 and immediately widened back to fp32 before the next op. This is what "bf16 inference" means in production serving (vLLM, HF `transformers` with `torch_dtype=bfloat16`) and is the regime RepDL names as its target and arXiv:2606.00279 actually emulates.

**This memo recommends (b), narrowly scoped**, because (a) is already done (v0.2 is in production as a private spec) and claiming it as "CIS-2.5" would not be a new contract, just a restatement. (b) is the harder, more valuable claim — it is what RepDL wants and cannot yet do, and what 2606.00279 does only by hardware-emulation rather than spec-conformance. The rest of this memo designs (b).

### 1.2 Conversion points, with RNE

Two conversion directions exist and they are not symmetric:

- **bf16 → fp32 (widening): exact, no rounding decision.** Same formula as CIS2_SPEC_v0.2 §4.1 (`(b as u32) << 16`), applied both to weights at load and to any bf16 activation before it re-enters fp32 compute. This is a pure bit operation; there is nothing for two implementations to disagree about, on any ISA.
- **fp32 → bf16 (narrowing): lossy, requires a pinned rounding rule.** This is the new normative surface CIS-2.5 must add. Round-half-to-even (RNE) on the 16 low mantissa bits, defined bit-for-bit (not delegated to a compiler intrinsic or a hardware instruction — see §2):

```
# f32 bits: [sign(1) | exp(8) | mantissa(23)]
# bf16 bits: [sign(1) | exp(8) | mantissa(7)]  (top 16 bits of f32, exponent field identical width/bias)

fn f32_to_bf16_rne(x: f32) -> u16:
    bits = x.to_bits()                      # u32
    if x is NaN:  return (bits >> 16) as u16 | 0x0040   # canonical quiet NaN, top bit of truncated mantissa forced set — pin one convention (below)
    rounding_bias = 0x7FFF + ((bits >> 16) & 1)          # ties-to-even: +1 extra if the retained bit is odd
    rounded = bits.wrapping_add(rounding_bias)
    return (rounded >> 16) as u16
```
    This is the standard "round-nearest-even via biased add, then truncate" bit trick (used by, e.g., TensorFlow's and PyTorch's own bf16 cast implementations) — it is a closed-form integer operation, not a hardware call, so it is trivially the same on x86-64 and aarch64 scalar cores. **NaN handling and negative-zero handling MUST be pinned explicitly in the real spec text** (this memo flags them; it does not resolve them — see §6, Risk 3). Subnormal fp32 inputs: FTZ/DAZ is already pinned on for the fp32 engine (CIS2_SPEC_v0.2 §1.3); a narrowing conversion never encounters a subnormal fp32 input under that pin, so no additional rule is needed there.

- **Conversion points (where narrowing happens) — this is a design knob, not yet fixed.** Two candidate granularities, ordered from more conservative (closer to real bf16-serving semantics, more spec surface) to less:
  1. **Per-op boundary**: narrow after every major op (attention block output, MLP block output) — matches what a real bf16-weights `torch_dtype=bfloat16` HF model actually does at layer boundaries when no autocast is in effect, because parameters are bf16 and the framework's default op dispatch keeps activations in the parameter dtype unless told otherwise.
  2. **Residual-stream-only**: narrow only the residual stream between blocks, keep intra-block activations (attention scores, MLP hidden) in fp32. This is closer to mixed-precision autocast serving (`torch.autocast`), not plain bf16-weights serving, and is a different reference to be honest about.
  **Recommendation: pick (1).** It matches the plain-bf16-weights HF reference most directly (see §3), needs no autocast-policy modeling, and gives the cleanest one-sentence contract: "every tensor that would exist in bf16 dtype in an unmodified `torch_dtype=bfloat16` forward pass is bf16 in this spec too; everything else (attention-score softmax denominators, RoPE angle tables, RMSNorm's internal square/mean/rsqrt, all transcendental evaluations) stays fp32, unchanged from CIS-2 v0.2 §5–§8." That single sentence is the entire new normative surface beyond CIS-2 v0.2 — everything else is inherited unmodified.

### 1.3 fp32 accumulate, pinned reduction order

**Unchanged from CIS-2 v0.2 §5.1: strictly sequential left-to-right, index order `0, 1, ..., n-1`.** No pairwise tree, no chunking, no reordering by magnitude — the same order already normative for every dot product in the fp32 engine. **Correction (re-checked 2026-09-03, after this memo's first commit):** a pinned-tree-reduction candidate does exist — `cis2-fp` branch `cm/e18c-pinned-tree-reduction` (checked out at `~/projects/cis2-fp-e18c`), created 2026-09-03 05:00:28, four minutes before this memo's first commit (05:04:32). It carries `docs/design/CIS2_V04_TREE_REDUCTION.md` (commit `f88bff4`, landed 05:05:40, ~1 minute after this memo), a v0.4-CANDIDATE (not yet normative) design: block size `B = 32` (one CUDA warp), a fixed 5-round pairwise butterfly within each block, and an explicit ragged-tail zero-pad rule for reduction lengths not divisible by 32 (softmax's `pos + 1` window is the case that actually exercises it). Its own text is explicit that it produces **new, v0.4-CANDIDATE digests, not equal to the v0.3b sequential ones** — it does not claim to reproduce this memo's sequential digests, and it is motivated by GPU tractability (E18c, following the E18/E18b memo), not by anything in CIS-2.5's scope. **This does not change CIS-2.5's design choice**: this memo's contract is CPU-only (§1 above), and CIS-2 v0.2's sequential order is what a CPU-only spec inherits regardless of what a GPU-motivated CANDIDATE branch does. But the earlier claim that no such branch or `docs/design/` directory existed was wrong — it existed at the time of writing, and a future reader implementing CIS-2.5 must know the two orders are deliberately different, not that only one was ever proposed. If a GPU leg later requires a blocked/tree order for tractability, `cm/e18c-pinned-tree-reduction`'s B=32/zero-pad design is the existing candidate to reconcile with, not a hypothetical to design from scratch.

Because every matmul/attention/RMSNorm reduction in CIS-2.5 operates on **fp32-widened** values (bf16 inputs are widened to fp32 before entering the dot product, exactly as weights already are per §4.2), the reduction primitive itself is byte-for-byte the one already conformance-tested in CIS-2 v0.2 — CIS-2.5 adds a rounding step at tensor boundaries, not a new numeric core.

### 1.4 Transcendentals unchanged

`exp`, `sin`, `cos`, `ln` stay exactly as pinned in CIS2_SPEC_v0.2 §6 (Cephes-pattern polynomials, strict left-to-right Horner evaluation, no FMA, pinned coefficients) — they only ever see fp32 inputs (RoPE angles, softmax exponents, RMSNorm's `rsqrt` argument), none of which are among the tensors narrowed to bf16 under §1.2's per-op-boundary rule (attention scores pre-softmax and RMSNorm's internal scalar reduction are explicitly fp32-only, matching real bf16-weights inference where softmax and normalization are almost universally computed in fp32 even under a bf16 parameter dtype, to avoid softmax overflow and norm instability — this is standard practice, not a CIS-2.5 invention, and should be footnoted as such with a citation to a framework doc when the real spec is written).

### 1.5 Receipt fields (additions to CIS2_SPEC_v0.2 §12)

CIS2_SPEC_v0.2 §12 already defines a receipt/digest format (witness chain, table digests, per-token logit hashing). CIS-2.5 needs exactly these additions, appended, not restructured:

| New field | Value | Why |
|---|---|---|
| `spec_version` | `"CIS-2.5-v0.1"` (or whatever the real doc is versioned) | Existing convention (CIS2_SPEC_v0.2 §12 already versions itself; §16 is a changelog) — a receipt must say which contract it claims conformance to, since 2.5 and 2.0 receipts are not comparable (different bits at every layer boundary). |
| `activation_precision_policy` | one of `"bf16-storage-only"` (= CIS-2 v0.2's existing behavior) or `"bf16-layer-boundary"` (= this memo's §1.2 design) | Without this field a verifier cannot tell which of the two designs in §1.1 a given receipt claims — this is the single field that makes CIS-2.5 receipts unambiguous against CIS-2.0 ones. |
| `bf16_narrow_rule_digest` | SHA-256 of the pinned narrowing-conversion routine's reference bit-pattern test vectors (e.g. all 2^16 possible fp32-exponent/mantissa boundary cases near a tie) | Same pattern as the existing `table_digest` for RoPE `inv_freq` (§7.2 of v0.2) — pins the one genuinely new lossy operation this spec adds, the same way v0.2 pinned RoPE's lookup table. |
| Everything else in §12 (witness chain, per-token logit SHA-256, item order) | **unchanged** | CIS-2.5's receipt is CIS-2 v0.2's receipt plus the two fields above; it does not redefine anything already normative. |

## 2. Why hardware bf16 paths cannot be used, and what can

**Cannot use, without vendor-order knowledge:**

- **NVIDIA tensor cores (bf16 × bf16 → fp32 accumulate).** PTX documents that BF16 MMA instructions accumulate in fp32 (confirmed: every BF16 MMA op in the PTX ISA guide is fp32-accumulate-only), but the *internal order* in which a tile's partial products are summed is a property of the specific SASS/CUTLASS kernel configuration selected at compile/launch time (tile shape, K-splitting, warp-level MMA layout), not a documented, stable, cross-generation contract. arXiv:2606.00279's own bit-exact CPU emulator has to "mirror the sequential K-walk used by the target kernel's mainloop (CUTLASS's default configuration)" and store the FP32 accumulator to bf16 between projection stages exactly where the *specific kernel* does — i.e., the only publicly demonstrated way to get bit-exact agreement with an NVIDIA tensor-core bf16 result is to reverse-engineer and clone one specific kernel build's internal reduction order, which is neither documented by NVIDIA nor stable across architectures/CUTLASS versions. A conforming CIS-2.5 implementation that used tensor cores directly would be pinned to whatever order the driver/compiler picked for a given GPU generation, defeating the whole point of a spec a third party can implement independent of NVIDIA's internals.
- **Intel AMX (TDPBF16PS / bf16 dot-product-accumulate tile instruction).** Confirmed from the instruction reference: each BF16 pair is converted to fp32, multiplied, and accumulated into the destination tile using fp32 FMA with RNE rounding and FTZ/DAZ set — this part *is* documented and RNE-consistent. But the accumulation is a **fused multiply-add** (the instruction reference explicitly describes FMA-style accumulation), and CIS-2's existing fp32 engine forbids FMA entirely (CIS2_SPEC_v0.2 §1.4, checked by disassembly gate for `vfmadd*`/`fmadd`). An AMX-computed dot product is therefore bit-divergent from the CIS-2 §5.1 sequential no-FMA reduction by construction, on the very first accumulation step, independent of any GPU question. AMX also gives no per-pair public guarantee about the SIMD-lane grouping order within a tile's row (the "set of SIMD dot-products" the reference describes is itself a parallel reduction over lanes before the FMA into the tile accumulator) — a second, non-FMA order-of-summation difference on top of the FMA one.
- **ARM BFDOT / BFMMLA.** Confirmed from ARM's own architecture reference: these instructions use **only** the non-IEEE round-to-odd (sticky) rounding mode for every internal multiply and add — not round-to-nearest-even. This is not a subtle ordering difference; it is a different rounding *rule* than IEEE-754 RNE, applied to every internal step, and it cannot be reconciled with a spec built on IEEE RNE fp32 arithmetic (CIS-2 v0.2's entire numeric core) by any choice of reduction order — round-to-odd is deliberately non-associative-preserving in a different way than IEEE rounding is, and is documented as such for exactly the reason that it is meant for cheap intermediate accumulation, not for bit-reproducible final results.
- **x86 AVX512-BF16 conversion instructions (VCVTNEPS2BF16 / VCVTNE2PS2BF16) — a narrower case.** These *do* use RNE and *do not* consult MXCSR (confirmed from Intel's own reference: "Round to nearest (even)... MXCSR is not consulted nor updated"), so the **narrowing conversion itself** is architecturally pinned and would in principle agree with the software RNE routine in §1.2, provided the bit-trick formula there is verified equivalent (it should be, since both implement the same IEEE RNE rule on the same 16-bit truncation boundary — this is a checkable claim, not yet checked; flag as a to-do before the real spec ships). What remains disallowed is `VDPBF16PS` (the bf16×bf16→fp32 dot-product instruction), because — like AMX's `TDPBF16PS` — its accumulation is a fused, hardware-internal reduction over an unpinned number of lanes with no documented order guarantee equivalent to CIS-2's explicit sequential rule.

**Can use:** scalar or SIMD **widen-only** bf16→fp32 (the exact bit-shift, safe on any ISA, already proven in CIS-2 v0.2), the software RNE narrowing routine in §1.2 (a closed-form integer bit operation, not a hardware call), and the existing CIS-2 pinned fp32 math (§5.1 sequential dot product, §6 Cephes transcendentals) for every actual arithmetic step. This means a CIS-2.5-conforming implementation is, numerically, **the existing CIS-2 v0.2 engine with narrowing calls inserted at the boundaries §1.2 names** — no new arithmetic kernel is required, which is what makes the ≤1-week plan in §4 plausible.

## 3. The honest quality claim

**bf16 storage is lossless with respect to the reference only if the reference is itself defined on bf16-rounded weights** — this is not new to CIS-2.5; CIS2_SPEC_v0.2 already states its own scope this way (§0: "does not claim... cross-framework agreement... as a conformance requirement; CIS-2 conformance is defined relative to this document's own bits, not to any third-party framework's output"). CIS-2.5 inherits and sharpens this for activations too:

- **What the claim is not:** "CIS-2.5 output equals what an fp32-native model would have produced." It does not, and cannot — bf16 has 8 fewer mantissa bits than fp32, and narrowing an fp32 activation to bf16 at a layer boundary is a real, lossy, information-destroying step (this is why §1.2's `bf16_narrow_rule_digest` matters: it is the one place genuine precision is thrown away, and it needs to be pinned and auditable, not glossed over).
- **What the claim is:** "CIS-2.5 output is bit-identical, across independently-compiled x86-64 and aarch64 implementations, to what this written specification defines as correct" — and the specification's own definition of correct is itself already-bf16-lossy at every layer boundary named in §1.2, by construction. The reference is not "the fp32 model, approximated"; the reference **is** the bf16-boundary-narrowed computation, full stop. Framed this way there is no accuracy claim being smuggled in — only a reproducibility claim, exactly as CIS-2 v0.2's own §0 already insists for its narrower (weights-only) case, extended to cover the activations §1.2 adds.
- **Why this distinction matters for the priority claim:** RepDL and arXiv:2606.00279 both work with *real* bf16-serving stacks (HF `transformers`/vLLM with `torch_dtype=bfloat16`, or a live GPU's actual tensor-core execution) as their reference — i.e., their "correct" is defined by whatever a specific vendor stack happens to compute, which is exactly the problem CIS-2.5 is trying not to have (per §2, that stack's internal order is unpublished for the GPU case). CIS-2.5's reference is a **self-contained written spec text**, checkable without running anyone's GPU stack at all — the same "spec text alone is sufficient" property CIS-2 v0.2 already demonstrated for fp32 (two independent clean-rooms, `verify2/` Rust and `verify3/` C11, reproduced digest `a0c563ef804f50413b7fb6619ae4afe9b51b1ffa7655e944221393e85d6261da` from spec text alone with no access to `src/` or to each other — `~/projects/cis2-spec` README "Provenance", and `2026-09-02-CIS-EDGE-AND-PRODUCT.md` §1). CIS-2.5 has not yet run this clean-room test (§4, item 5) — until it has, "spec-sufficient" is a design goal for CIS-2.5, not yet a demonstrated property, and must not be claimed as done.

## 6. Risks and what would kill it

1. **The narrowing rule's edge cases (NaN, negative zero, ties at the very top of the mantissa range) are not yet pinned.** §1.2 flags this explicitly and leaves it open; it is the single piece of genuinely new normative surface CIS-2.5 adds beyond inherited CIS-2 v0.2 text, and getting it wrong (e.g., two implementations disagreeing on which NaN payload bit pattern to emit) would break bit-identity on the very first divergent input, independent of everything else in this memo being correct. **Kill trigger:** if Day 1's exhaustive 2^32-case check (§4) finds the software RNE routine disagrees with hardware `VCVTNEPS2BF16` on any input class that actually occurs in SmolLM2-135M's activation range, the spec text must pin the *disagreeing* case explicitly (not silently pick one), or the whole "spec text alone is sufficient" property (§3) is compromised before it is even tested.
2. **The per-op-boundary granularity (§1.2, option 1) may not match any real HF/vLLM reference closely enough to be a fair "this is what bf16 inference does" claim**, if a real `torch_dtype=bfloat16` forward pass under HF `transformers`' actual default op dispatch narrows/widens at different points than this memo assumes (e.g., some ops may upcast internally without the user ever seeing an intermediate bf16 tensor materialize). This has **not been empirically checked against a live HF run** — it is stated as the design's premise, not verified. **Kill trigger:** if Day 1's spec-writing pass (or an oracle run against real HF `transformers`, the same style as `E15d_bc_RESULT.md`) shows the actual reference materializes bf16 tensors at different boundaries than §1.2 assumes, the contract's "matches real bf16-weights serving" framing in §3 must be corrected or dropped before any public claim — CIS-2.5 would still be a valid, well-defined spec, just not one that maps cleanly onto "what production bf16 serving does," which is the framing that makes it a priority claim rather than an arbitrary bf16 variant.
3. **A hostile reviewer credits arXiv:2606.00279 as "already did bf16 CPU-GPU bit-exact"** and treats CIS-2.5 as redundant. The rebuttal (§3, §5 table) is that 2606.00279 needs a real GPU and per-architecture recalibration and cannot be implemented by a third party from text alone, while CIS-2.5 needs neither — but this rebuttal is currently untested: **CIS-2.5 has not yet run its own clean-room check** (§4 Day 5). Until a second, isolated implementation reproduces the digest from spec text alone, "spec-sufficient" is asserted, not demonstrated, for the bf16 case specifically (v0.2's fp32 case has this evidence already; 2.5 does not yet). **Kill trigger:** if Day 5's clean-room attempt fails to reproduce the digest, the "spec text alone is sufficient" framing must not be used for CIS-2.5 publicly until it is fixed and re-verified — the same evidentiary bar CIS-2 v0.2 already had to clear (E15e/E15g/E15j/E15k cleanroom results) before any public claim.
4. **This is still a CPU-only claim** (per §1.3, no GPU reduction order is assumed or pinned). If the eventual goal is a bf16 CPU↔GPU claim (matching what RepDL/2606.00279 are actually chasing), CIS-2.5 as designed here is a necessary but not sufficient step — the GPU leg would need its own reduction-order design (E18-style), and §2's finding that hardware bf16 tensor-core/AMX/BFMMLA paths are unusable without vendor-order knowledge means a conforming GPU implementation would have to forgo tensor cores entirely and do scalar/CUDA-core bf16-widen-then-fp32-pinned-math, which is a real, uncosted engineering question this memo does not resolve (out of scope, flagged for a future E-series task, likely paired with the existing E18b-gpu CUDA-portable work in `cis2-fp` PR #2/#3).
5. **Publish-policy risk, not technical risk.** cis2-fp is PRIVATE (verified 2026-09-03, per house rules). This memo and any resulting spec/branch stay private and undecided on publication, same as CIS-2 v0.2's own public-push status (`2026-09-02-CIS-EDGE-AND-PRODUCT.md` notes v0.2/v0.3b's public push is "still gated on Justin's PUBLISH?" decision, unresolved as of that report) — nothing here changes that gate, and no "first" or priority-claim language should be used publicly before Justin decides to publish and before §4's PASS criterion and §6 item 3's clean-room check both succeed.

## Summary (10 lines)

CIS-2 v0.2 already stores weights as bf16 and widens them losslessly to fp32, computing entirely in fp32 — that is not yet a "bf16 inference" claim in the sense RepDL and arXiv:2606.00279 use the term. This memo designs CIS-2.5: bf16 at weights **and** activation layer-boundaries (matching real `torch_dtype=bfloat16` serving), fp32 internal accumulate, with a new pinned RNE narrowing rule (a closed-form bit-trick, exhaustively checkable) as the only new normative surface — everything else (sequential no-FMA reduction, Cephes transcendentals, receipt format) is inherited unmodified from CIS-2 v0.2. Hardware bf16 dot-product paths — NVIDIA tensor cores (kernel-specific undocumented order), Intel AMX (FMA-fused), ARM BFDOT/BFMMLA (non-IEEE round-to-odd) — are all shown, from primary sources, to be incompatible with a portable IEEE-RNE/no-FMA spec; a conforming implementation instead does scalar bf16-widen plus the existing pinned fp32 engine, so no new arithmetic kernel is needed. The honest quality claim is explicit: bf16 storage/activation narrowing is lossless *relative to a reference defined on bf16-rounded values*, not relative to an fp32-native model — a reproducibility claim, not an accuracy claim. Implementation is a ≤1-week plan (spec text + exhaustive narrowing-rule check, engine change, x86/aarch64 digest run, PASS = matching digests, then a clean-room reproduction attempt) with zero new numeric kernels. **Correction:** `docs/design/CIS2_V04_TREE_REDUCTION.md` / branch `cm/e18c-pinned-tree-reduction` does exist in `cis2-fp` (created before, landed just after, this memo's first commit) — it is a GPU-motivated v0.4-CANDIDATE (B=32 blocked tree, zero-pad ragged tail) that explicitly produces different digests from the v0.3b sequential path and does not claim to supersede it; this memo still uses the existing sequential order for its CPU-only contract, but the two designs coexist deliberately and are not the same thing. Prior art (RepDL, arXiv:2606.00279, RepOps, OzBLAS) either hasn't attempted bf16 cross-hardware yet, or achieves it only by emulating one specific vendor's undocumented kernel internals rather than converging on shared spec text — that gap is what CIS-2.5 targets. Two risks are unresolved and explicitly not yet checked: whether the per-op-boundary narrowing granularity actually matches real HF/vLLM bf16 serving, and whether a second clean-room implementation can in fact reproduce the digest from text alone (v0.2 has this evidence; 2.5 does not yet). Nothing here is public-ready: cis2-fp is private, the v0.2 public-push decision is still pending Justin, and no priority-claim language should be used before the PASS criterion and the clean-room check both succeed.
