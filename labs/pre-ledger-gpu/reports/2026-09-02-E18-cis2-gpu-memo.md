# E18 — CIS-2 on GPU: design memo (research workflow wf_43bbc2d9-074, 2026-09-02)

**Question.** Can the CIS-2 v0.3b fp32 forward pass be made bit-identical between the CPU reference (x86_64 + aarch64) and a CUDA implementation on free Kaggle GPUs, at usable speed?

**Decision (Fable, 2026-09-02, autonomous):** implement the *strict* v0.3b spec on GPU first — no spec revision. Reasons:
(1) the GPU is a third ISA implementing the same spec (critique §4); three independent implementations converging on one digest is the strongest form of the claim;
(2) for SmolLM2-135M the spec's left-to-right per-output reductions map onto the ordinary one-thread-per-output kernel (matvec: N threads × K serial; attention: one thread per (head, query) serial over keys; RMSNorm: one thread per row) — slower than cuBLAS, not absurd, and enough for a feasibility first;
(3) a pinned blocked-tree revision (v0.4) is a *performance* leg (E18c) and must not precede the feasibility result, or a failure could not be attributed.
Method: a single-source CUDA-portable C++ implementation in cis2-fp (private). Its **host build** (clang++, `-ffp-contract=off`, FTZ/DAZ via MXCSR, no libm — Cephes ports mirrored from the Rust reference) must reproduce the Rust digest on penguin first (E18b-host); the identical source then compiles under nvcc on Kaggle (`-fmad=false -ftz=true -prec-div=true -prec-sqrt=true`, no `-use_fast_math`, no SFU intrinsics) (E18b-gpu). Anything that differs on the GPU is then isolated to compiler/hardware arithmetic, found by a per-layer/per-op digest trace.
Scope of any "first" claim (critique §5): *fp32* cross-architecture bit-identity CPU↔GPU from a spec; integer/fixed-point cross-arch identity is known (CIS-1 already did it).
Prior art status: none found claiming CPU↔GPU bit-identical transformer inference; Thinking Machines (2025) and SGLang solve same-GPU batch-invariance; ReproBLAS/exblas/SLEEF address reproducible BLAS/libm, not a full model — absence of hits, not a proof (critique §1).

## Synthesis (as returned by the workflow)

# E18 Synthesis: CIS-2 CPU–GPU Bit-Identity

**Answer:** Bit-identical fp32 forward passes between the CIS-2 CPU reference and CUDA are **not achievable via stock cuBLAS/cuDNN**, but **are plausibly achievable via hand-written CUDA kernels** implementing a pinned reduction order — at a quantifiable (not absurd) speed cost. No published work claims CPU↔GPU bit-identity today; the closest prior art (Thinking Machines Lab, Sept 2025) solves a narrower problem (same-GPU batch-invariance), leaving this open as a plausible first if executed. (https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)

**Why cuBLAS is disqualified:** NVIDIA's own docs state cuBLAS determinism guarantees are scoped to "the same architecture and the same number of SMs" — not cross-architecture, and offer no per-call flag to disable FMA contraction (that control exists only at `nvcc -fmad=false` for hand-written kernels). Reduction order inside cuBLAS GEMM is heuristic/ALGO-selected, not user-specified. (https://docs.nvidia.com/cuda/cublas/index.html)

PyTorch's own docs confirm the mechanism and the limit: `torch.use_deterministic_algorithms()` explicitly states results "cannot be guaranteed reproducible between CPU and GPU even with identical seeds," and names the root cause as backends performing "floating-point accumulation in a different order" — the same non-associativity problem CIS-2 targets. (https://pytorch.org/docs/stable/notes/randomness.html)

**Three ranked options:**

1. **Hand-written CUDA kernels, no FMA, pinned serial or blocked-tree reduction (recommended).** Write matmul/RMSNorm/attention/RoPE kernels in raw CUDA with `-fmad=false`, explicit accumulation order, and software (Cephes-pattern) transcendentals instead of SFU intrinsics. This is the only path with any precedent — Thinking Machines' `batch_invariant_ops` proves fixed-reduction-order kernels can be built and shipped, going from 18 unique outputs to 1 across 1000 runs, at ~20% cost for matmul alone and 1.6–2.1x for full deterministic serving (bf16, not CIS-2's regime). (https://github.com/thinking-machines-lab/batch_invariant_ops)

2. **Revise the spec to CIS-2 v0.4 with a pinned deterministic tree/block reduction (not strict left-to-right), adopted by both CPU and GPU implementations.** This is the direction the TBIK paper and SGLang's production determinism stack both point toward — fixed split-size (not split-count) reductions to decouple order from batch size. v0.4 would need to byte-exactly specify block size, tree shape, and accumulation dtype so the CPU reference stays conforming. SGLang reports 34.35% average slowdown (vs Thinking Machines' 61.5%) with 2.8x recovered via CUDA graphs — a citable "usable, not absurd" range. (https://lmsys.org/blog/2025-09-22-sglang-deterministic/, https://arxiv.org/abs/2511.17826)

3. **Keep strict left-to-right sequential CPU-spec reduction on GPU via serial per-output-element kernels.** Technically fastest to reason about correctness-wise but forfeits nearly all GPU parallelism in the reduction dimension — no source quantifies this cost directly, so it should be treated as the fallback baseline to measure against, not the target.

**Risks:** (a) SFU-only transcendental paths on some GPU generations may make software exp/sin/cos slower or harder to pin than expected — no source addresses this directly, flag as untested; (b) cuDNN attention backends have non-deterministic backward passes by default and CUDNN_ATTENTION backward is disabled entirely under strict determinism, per PyTorch docs — irrelevant to forward-only CIS-2 but a hazard if the project later touches training; (c) the closest adjacent paper (arXiv:2606.00279) is dated 2026-05-29, ahead of normal cutoff conventions, and its bibliographic details are unverified against a second source — treat as provisional, do not cite its numbers without independent confirmation. (https://arxiv.org/abs/2606.00279, https://pytorch.org/docs/stable/notes/randomness.html)

**What Justin must decide:** (1) commit to hand-written CUDA kernels (Option 1) as the near-term Kaggle experiment, or hold for a spec revision (Option 2) first; (2) whether a "first" claim should be staked publicly given publish-policy (ask before publishing disruptive results) — this is genuinely novel-looking territory; (3) budget for the 12h T4 Kaggle session against the SmolLM2-135M fp32 target now, given cheap-agent-only guidance is otherwise in force.

## Critic pass

1. Unsupported: "no published work claims CPU↔GPU bit-identity" is a negative claim backed by absence of search hits, not a source — also ignores existing cross-platform reproducible-numerics libraries (SLEEF, ReproBLAS, and Kahan/pre-rounding techniques for reproducible summation, e.g. Demmel/Nguyen) that address exactly this problem for BLAS.
2. Unsupported: "SFU intrinsics" being the default transcendental path is wrong — CUDA `expf`/`sinf` are already software (compiler-emitted), IEEE-rounded to ~2 ulp, and only `__expf`/`-use_fast_math` hit the SFU; the risk (a) is overstated and the Cephes-port cost is understated as "flag as untested" when it is routine.
3. Unsupported: "plausibly achievable ... quantifiable speed cost" cites bf16 batch-invariance numbers (20%, 1.6–2.1x, 34%) that measure a different property (order fixed across batch sizes, not matched to a CPU serial order); none of those systems removed FMA, so the fp32 no-FMA cost is uncited.
4. Missing angle: the CPU side is not fixed either — x86 AVX2/FMA vs scalar SSE vs aarch64 already differ in contraction and vectorized reduction order; CIS-2's existing cross-ISA result (A39, spec-driven) is the real precedent and the synthesis never leverages it: the GPU is just a third ISA implementing the same spec.
5. Missing angle: the "first" claim needs a scoped statement — cross-arch bit-identity is trivially achievable with integer or fixed-point arithmetic (CIS-1 2B all-integer already did this); the novelty is fp32-specific and must be framed that way or reviewers will dismiss it.
6. Missing: Kaggle T4 has no fp32 tensor cores concern, but `-fmad=false` only affects hand-written kernels; any PyTorch glue (embedding, softmax, argmax) must also be hand-written or verified — the synthesis leaves the boundary undefined.
7. Change this recommendation: swap the ranking of Options 1 and 2. Writing kernels against the current strict left-to-right spec (Option 1 as written) forces Option 3's serial reduction; pinning a blocked-tree order in the spec first (v0.4) is what makes Option 1 fast, so Option 2 is a prerequisite, not an alternative. Do the spec revision (small, cheap, no GPU needed) first, update the CPU reference, then write the CUDA kernels against v0.4.
8. Provisional-source hygiene is good on arXiv:2606.00279, but the same skepticism should apply to arXiv:2511.17826 (described as TBIK) — its numbers are not restated so it is harmless, but its attribution is unverified.
9. Decision (3) framing conflicts with memory: Kaggle is designated as ALICE training hardware and the cheap-agent budget rule applies to Fable tokens, not GPU hours — the 12h T4 experiment is not blocked by the budget guidance the synthesis invokes.
10. Net: the answer direction is right; the ranking is inverted and the "first" claim is over-broad.
