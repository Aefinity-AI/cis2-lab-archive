# E15c adversarial verification — cis2-fp cm/e15c-cross-isa

Worktree used: `~/projects/cis2-fp-e15c` (pre-existing worktree at HEAD
05187dc, branch cm/e15c-cross-isa). No timing numbers reported (Rule A).

## (1) What does the digest cover?

**PASS — stronger than the task assumed.** `CIS2_REF digest` (the
`witness_digest` in `src/main.rs:349-419`) is a SHA-256 chain over: weight
sha256 + tokenizer sha256 + config sha256 + prompt token ids, then for
each of the 16 generation steps, the **full fp32 logit vector's raw bit
pattern** (`v.to_bits().to_le_bytes()`, all 49152 vocab entries,
`src/main.rs:401-405`) plus the argmax token id — not just argmax token
ids. A separate `argmax_digest` (token ids only) is also printed but is
not what "CIS2_REF digest=" refers to. So cross-ISA bit-identity is
claimed (and was tested) over full logits at every step, which is a much
harder bar than argmax-only.

Given that, the "argmax slack" question is secondary, but computed anyway
(instrumented `src/main.rs` locally, reverted before finishing — see
below): min top1/top2 logit margin across the 16 steps is
**0.0117 (step 13)**, vs typical margins of 0.3-5.2. This means even if
the digest were argmax-only, most steps would tolerate far more than 1
ULP of divergence before flipping — but step 13's margin is thin enough
that a bug producing ~0.01 logit-scale divergence (plausible for a real
cross-ISA libm/FMA bug, not for the fp32-ULP noise floor) could flip one
token. Not applicable here since the actual claim binds full logit bits,
not argmax.

## (2) Are the gates real?

- **No FMA**: PASS. `src/math.rs` uses only separate `let p = a*b; acc =
  acc + p;` — never `.mul_add`. Mechanically gated by
  `scripts/no_fma_gate.sh` (grep + objdump). I rebuilt locally with
  `RUSTFLAGS="-C target-cpu=native"` (this CPU has `fma` in
  `/proc/cpuinfo` flags, so LLVM had FMA available to auto-contract into)
  and ran `objdump -d | grep -icE "vfmadd|vfnmadd|vfmsub|vfnmsub"` → **0**
  hits, same as the default release build (also 0). Digest unchanged
  (see item 3). Confirms Rust/LLVM truly never auto-fuses without
  explicit fast-math, even when the target supports FMA.
- **Reduction order**: PASS. `dot_seq`/`sum_seq`/`softmax_seq` denominator
  (`src/math.rs:40-58,242-259`) are plain `for` loops with a scalar
  accumulator, no `.iter().sum()`, no `rayon`/SIMD intrinsics, nothing an
  optimizer could legally reorder (Rust float ops are not associative and
  LLVM doesn't reorder fp reductions without fast-math). Left-to-right by
  construction, not just by convention.
- **libm calls**: PASS, and this is the strongest part of the design.
  `exp_pinned`/`sin_pinned`/`cos_pinned` (`src/math.rs:100-227`) are
  self-contained Cephes-style polynomials using only `+ - * /` and
  `.floor()`/`.round()` — **zero calls to platform libm exp/sin/cos**.
  `rsqrt_cr` uses only `.sqrt()` and `/`, both IEEE-754-mandatory
  correctly-rounded ops (glibc x86_64 `sqrtsd`/aarch64 `fsqrt` are both
  hardware, both correctly rounded — no libm involved). This sidesteps
  the classic glibc-x86-vs-aarch64 transcendental divergence bug class
  entirely, by construction, rather than by hoping the platform libms
  happen to agree.
- **FTZ/DAZ / FPCR.FZ**: PASS. `src/denormal.rs` sets and reads back
  MXCSR bits 15/6 (x86_64) or FPCR bit 24 (aarch64) via inline asm,
  asserts the readback, and there's a real adversarial unit test
  (`ftz_daz_pinned_and_denormal_input_flushed`) using `black_box` to stop
  LLVM folding the subnormal add away. Ran on both ISAs in CI (job logs
  confirm `cargo test --release` passed on both legs).
- **Compiler flags / target-feature**: PASS, nothing hidden. `Cargo.toml`
  has no `RUSTFLAGS`, no `target-feature`, `opt-level=3` only. No
  `rust-toolchain.toml` pin exists (both CI legs happened to resolve to
  `stable` = `rustc 1.98.0 (88d9e12ae 2026-08-18)` — see item 4 — but this
  is not a hard pin and could drift on a future re-run days apart).

## (3) Local x86 rebuild variants — does the digest move?

Ran locally on this box (x86_64, `rustc 1.98.0`), reusing existing
`weights/` (no re-download):

| build | CIS2_REF digest | inv_freq table_digest | FMA in .text |
|---|---|---|---|
| default `cargo build --release` (opt-level=3, Cargo.toml default) | `ba88708b...09dd0f` | `da9f6dcf...52e7bb` | 0 |
| `RUSTFLAGS="-C opt-level=0"` | `ba88708b...09dd0f` | `da9f6dcf...52e7bb` | n/a |
| `RUSTFLAGS="-C target-cpu=native"` (AVX2+FMA available on this CPU) | `ba88708b...09dd0f` | `da9f6dcf...52e7bb` | 0 |

All three digests identical to the pre-registered target and to each
other. This is the cheapest available falsification attempt (hidden
FMA/reassociation would very plausibly show up under `target-cpu=native`
at opt-level 3) and it did not break. Commands run:
```
cargo build --release
RUSTFLAGS="-C opt-level=0" cargo build --release --target-dir <scratch>
RUSTFLAGS="-C target-cpu=native" cargo build --release --target-dir <scratch>
objdump -d <bin> | grep -icE "vfmadd|vfnmadd|vfmsub|vfnmsub"
```
(No cross-compiled aarch64 toolchain available locally to objdump an
aarch64 binary for `fmla`/`fmadd`; this was only checked indirectly via
the CI job's `no_fma_gate.sh` step, which ran the same grep+objdump gate
natively on the `ubuntu-24.04-arm` runner and passed.)

## (5) Torch oracle

Confirmed present: `docs/E15b_m1p5_CORRECTNESS.md` + `scripts/oracle_compare.py`.
Setup: `torch==2.13.0+cpu`, `transformers==5.16.1`, deterministic algorithms on,
TF32 off, single thread, `dtype=torch.float32`, same weights (sha256-matched),
same tokenizer/prompt. Result: **16/16 greedy token ids match exactly**; step-0
full-vocab logit comparison: max abs diff `8.96e-5`, relative diff `~3.98e-6`,
pre-registered bar was `<1e-2` relative — passed with ~4 orders of magnitude
margin. Correctly NOT bit-identical to torch (torch uses MKL/its own reduction
order and libm) — the paper is explicit this was never the goal; only
cross-ISA self-consistency of the Rust reference is bit-identical.

## Overall verdict

**Holds, with one caveat**: no hard Rust-toolchain-version pin in CI
(`rust-toolchain.toml` absent) — both legs happened to land on the same
`rustc 1.98.0` this run, but that's incidental to the workflow, not
enforced. Everything else checked (digest scope, FMA absence including
under `target-cpu=native` with FMA-capable hardware, reduction order,
libm avoidance for transcendentals, FTZ/DAZ pinning, same-commit/
non-cached CI execution, torch oracle tolerance) reproduced cleanly and
found no gap. Recommend: add `rust-toolchain.toml` pinning an exact
`rustc` version before treating this as durable/publishable, otherwise
no changes needed to the current result.
