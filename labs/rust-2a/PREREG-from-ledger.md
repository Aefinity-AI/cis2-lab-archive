QUESTION. Does a 1:1 Rust port of our C cap-1c trainer produce byte-identical checkpoints to the C original on every machine we have?

WHAT IS COMPARED. Rust port (static musl build for box4 and box5, default x86-64 target, locked dependencies, no std exp/ln/powf: the vendored pinned math is ported too, no mul_add, no fast-math equivalents) against the C original (cap1c_train.c 274 lines plus vendored mathpin 358 lines, gcc, the flags of the cap-1c run recorded). Model, data, initial weights and batch order: the C trainer writes its initial weights and its batch-order file once (sha256 of both recorded and checked by the Rust port at start); the Rust port reads them, so only the training arithmetic is under test. As an extra, reported with no label, the Rust port also ports the init generator and its output is compared to the exported init. Builds: Rust opt-level 0 and 3, C -O0 and -O2 (extra builds as in the cis2-oflags matrix); every digest is checked on all of them.
Reference digests: the 4 checkpoint SHA-256 values in R/2026-09-24-cap1c-c-trainer-cross-isa.md AND the digests produced by the C original rebuilt and run in the same session on penguin. If those two sets disagree the reference is broken and the lab is INVALID until explained.

METRIC AND LABELS (no gaps, no overlaps; every outcome other than PORT EQUAL is PORT DIFFERENT).
 PORT EQUAL (level with C): in the initial complete attempt, on every host that ran, and for every Rust build tried, all 4 checkpoint SHA-256 digests equal the reference digests (the result also states 0 fix cycles).
 PORT DIFFERENT (behind C): any digest on any host or build differs IN THE INITIAL COMPLETE ATTEMPT. The initial complete attempt is the initial Rust port build that runs all 4 checkpoints on penguin and is compared with the reference; it is fixed by commit hash before any fix is made, and its result is the label (the builder knows the target digests and could iterate until they match, so only the initial attempt measures the port). Every later fix cycle is reported separately: the number of build-and-compare cycles, the cause found in each, and the final result ("PORT EQUAL after <k> fix cycles"); a final match after fixes never turns a initial-attempt PORT DIFFERENT into PORT EQUAL. The step of the earliest differing checkpoint and the host are reported and the cause is diagnosed, not re-rolled for a better answer. A difference found only at Rust opt-level 0 or only at 3 is still PORT DIFFERENT and is reported with the build.
There is no TIE band on the equality check because digests are equal or not. The wall time has no label (see MEASUREMENT).

MEASUREMENT (no bar, expected values in advance; ESTIMATE). Reported separately: (a) in-process wall of the 200 training steps, measured inside each program with a monotonic clock; (b) whole-process wall including start, file reads and the 4 checkpoint SHA-256 computations. 5 reps per host, arm order rotated, median and every rep value shown. Rule A (LOG.md 2026-09-12 14:16Z; BOXES.md): wall times from box2, box3, box4 and box5 are informal and are written as such; only box1 wall times count as a measurement, and only after the box1 CPUQuota and thermal check is recorded (see rust-1 Rule A block). Digest runs are not timing and are unaffected. Expected: (a) Rust over C wall ratio between 0.8 and 1.25 with about 80 percent confidence, both in the millisecond to low-second range (torch took 8.2 s for 200 steps of a different model on box1, import included, R/2026-09-24-cap1-box1-training-manifest.md); (b) dominated by process start, file reads and hashing, so the two programs look alike. A ratio outside 0.8 to 1.25 in (a) is written as SURPRISE in the result; it changes no label. No sentence about whether Rust is worth it for training is written from this lab.
