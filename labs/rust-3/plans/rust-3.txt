BAR for rust-3 (written 2026-10-03 before any run). This is a BAR: it can come out against Rust, for Rust, or as a tie, class by class. Expected values are written below so a surprise is visible.

ANSWERS: LANGUAGE (our Rust model loader against our C model loader, same task, same fuzzing tool, same sanitiser). Third-party loaders (Python safetensors binding, torch.load, llama.cpp GGUF) are reported rows with no label and are labelled FRAMEWORK/third-party; they say nothing about our C or our Rust. It does not answer KERNELS.

QUESTION. When each of our model loaders is handed damaged or hostile-looking files by the same kinds of mutation for the same hour, how many distinct memory-safety bugs, controlled failures, hangs, over-allocations and wrongly accepted files does each one show?

WHAT IS COMPARED.
 Bar pair (LANGUAGE): R1 = the cis2_ref safetensors-reading path (our code plus the vendored safetensors crate source) against C1 = the verify3 weights loader. Both read the same safetensors layout of the same tiny model.
 Reported rows, no label: R2 = alice-rs loader (memmap2); R3 = Python `safetensors` binding (it is Rust underneath: counted as a second Rust row, not as a Python row); P1 = torch.load(weights_only=True) on torch 2.14.0 (pickle, a different format, reported separately); L1 = llama.cpp GGUF loader at the pinned commit built locally with ASan and UBSan (C++; it says nothing about our C).
Entry point rule (fixed now): every harness enters at the header and tensor-table parse function, below any pinned-weights-hash gate. verify3 stops on a weights hash other than the pinned model, which would reject every mutant at once and show 0 bugs; the gate is switched off in the harness of every arm and that is recorded. The harness maps the parsed tensors and reads the opening and closing element of each, so lazy loaders are exercised (stated in the result).
Seed file: a valid tiny 2-layer synthetic model of under 1 MB in each format (safetensors for R1, C1, R2, R3 as applicable; GGUF for L1; pickle zip for P1), made from the same weights.
Mutation operators (fixed now; the same seven operators for every format, applied structure-aware by one script that writes the same number of mutants per operator per format): O1 header-length field; O2 metadata or JSON key and value (GGUF key-value pairs for L1); O3 tensor offsets; O4 shapes including overflowing products; O5 dtype codes; O6 truncation at 100 cut points; O7 duplicate keys. The result is the starting corpus of each arm; the corpora differ by format and not in operators. Then coverage-guided fuzzing: libFuzzer in every arm, ASan in every arm, same flags (-max_len 1048576, -rss_limit_mb 1024, -timeout 10, -seed fixed per trial), 1 hour per arm in TWO trials of 30 minutes with two different fixed seeds (1 and 2, the same for every arm), run one after the other on the same host, one process, one core. Coverage-guided results are stochastic and -seed does not fix them, so a finding counts once across the two trials (dedup key) and the per-trial counts are also reported, so the run-to-run spread is visible. Rust arms: cargo-fuzz on nightly with -Zsanitizer=address. C and C++ arms: clang -fsanitize=fuzzer,address (UBSan is added as an extra build, reported separately and not counted in the bar). Time is matched, executions are reported and not matched.
Extra, reported and not counted in the bar: Miri on the Rust loaders and on the aegis-core unsafe blocks Miri can run (blocks it could not run are listed); UBSan build of C1; lines of loader source and `unsafe` lines per arm; findings per 1,000 loader lines.

CLASSES (never summed; each class reported with raw crash count, deduplicated count, and reproducer files).
 K1 memory-safety: an ASan report of heap-buffer-overflow, use-after-free, stack or global overflow, or SEGV on an unknown address. K2 controlled failure: a Rust panic or a C abort or failed assertion on malformed input. K2 is INFORMATIONAL: counts are reported with no RUST HIGHER or RUST LOWER label, because a panic on a bad header is correct behaviour and the C loader's error-code returns are not counted (a class asymmetry that would make Rust look worse for the same correct behaviour); the result words it "more controlled failures" or "fewer controlled failures". A Rust allocation-failure abort is K4 when the input is under 1 MB and the allocation request or resident memory exceeded 1 GB, otherwise K2. K3 hang: more than 10 s. K4 over-allocation: more than 1 GB resident from an input under 1 MB (libFuzzer rss limit). K5 wrongly accepted: the loader returns success for a file whose declared tensor sizes and offsets are inconsistent with the file length, decided by the differential oracle script state/plans/rust-lab/oracle/k5_oracle.py (checks sizes, offsets, overlaps and bounds against the file length). The script is committed at that path before registration and its sha256 is written into the bar by amend-bar before start; registration waits for it.
Deduplication key (fixed now, replaces any top-3-frames rule): (class, name of the deepest stack frame that lies in the arm's own loader source or its vendored dependency source, operator id of the minimised reproducer, or "libfuzzer" if no operator produced it). Minimisation (fixed now): every crash input is minimised with libFuzzer -minimize_crash=1 -runs=10000 (cargo fuzz tmin with the same flags for the Rust arms) before the key is computed; the operator id is that of the starting-corpus mutant that triggered the finding when it fired during the corpus replay pass before fuzzing, otherwise "libfuzzer".

LABELS (no gaps, no overlaps), per class, bar pair R1 against C1. nR = distinct findings for R1, nC = distinct findings for C1 in that class. RUST LOWER: nC - nR >= 2. TIE: |nR - nC| <= 1. RUST HIGHER: nR - nC >= 2. Four classes (K1, K3, K4, K5) give four labels; K2 is reported as counts with no label; there is no overall label and no sum. The result lists the four labels and the K2 counts side by side. Counts are expected to be in single digits, so many lines will read TIE; the result says "TIE (counts too small to separate)" when nR + nC < 3.

TRUST COLUMN. This lab is the trust column: per arm and class, counts; loader lines; `unsafe` lines in the loader; dependency count; format surface (number of header fields the loader parses). R1 loader lines are shown with and without the vendored safetensors crate source (a finding in that vendored code counts for R1, because it is part of the loader we ship), while C1 is our own code only. Explicit caveat written in the result: C1 parses one pinned bf16 format, so it may show fewer bugs because it is smaller (a loader-size effect), not because of the language; the per-1,000-lines figures are shown next to the counts.

EXPECTED (ESTIMATE, before any run). K1: R1 0 (about 90 percent), C1 0 or 1 (about 50 percent at least 1; no ASan run on our C exists, OURS.md Q7). K2: R1 1 to 3 (panics on bad headers are likely), C1 0 to 2. K4: R1 0 to 1 (a 14.5 GiB whole-file read was found before in cis2_ref, LOG.md 2026-09-18), C1 0 to 1. K3 and K5: both 0 to 1. Likely labels: TIE on K1, K3, K4, K5; K2 counts likely higher for Rust (informational, no label). Reported rows: L1 likely shows K1 findings (llama.cpp has 5 GGUF heap overflows in NVD, REPORTED, PRIOR-ART.md section 4); P1 shows K2 only. A K1 finding in R1 would be a SURPRISE.

INVALID (the affected class or arm gets no label; redo): an arm ran under its two 30-minute trials or without ASan; a different fuzz flag set or seed pair between R1 and C1; a K5 oracle whose sha256 differs from the one in the bar; the hash gate left on in any harness; a harness crash counted as a loader finding; mutants per operator differ between formats; the oracle script changed after the initial run; the harness for C1 and R1 does not exercise the same tensor reads.

HAZARDS AND DISCLOSURE. No network; all inputs are corrupted copies of our own model files fed to our own or locally built loaders on our own machines. Findings in third-party code (safetensors crate, llama.cpp, torch) go to NEEDS before any disclosure; nothing is published. A NEEDS item is added only at result time if such a finding exists.

FIXED NOW (may not change after the initial run): arms, entry point rule, operators, classes, dedup key, fuzz flags, 1 hour per arm as two 30-minute trials with seeds 1 and 2, the oracle script (path and sha256), labels and sentences. Recorded and frozen before the run: commits, compiler and nightly versions.

HOSTS AND MEMORY. No timing number is a label here (executions are reported, not labelled), so Rule A (box1-only timing) is not engaged; the fuzz hosts are unchanged. Fuzz runs on box1, one arm at a time, MemoryMax 4.5 GB under systemd-run --user, host idle; ASan builds with -j1. Miri on box3 (MemoryMax 2.8 GB). Penguin builds and light triage only (never timing, MemoryMax 800 MB). Box2, box4, box5 not used.
