## Known asymmetries between the two arms (read the IMPLEMENTATION sentence with these)
1. Patch size: unequal, numbers above.
2. Tokenizer: the bar lists a different tokenizer as an asymmetry. In plain mode neither arm loads or runs a tokenizer (prompt ids come from the work file); the Rust binary still links tokenizers and onig (about 4 MB, rayon linked, onig_sys C code) and sv5_driver never had one. File size and link set differ; the timed window and the memory of the running process do not include a tokenizer.
3. Loader: the bar says the Rust safetensors crate maps the weights file (mmap). cis2_ref reads it with std::fs::read into a heap buffer, deserializes over the slice, widens each tensor to a fresh Vec<f32>, then drops the buffer; verify3 reads it with fread into a heap buffer, widens each tensor into a malloc block, then frees the buffer (model.c line 202). Both use read(); neither maps. The memory sentence template "load methods differ (mmap, read())" is therefore not true for this pair (Pin P4). Anonymous bytes and PSS carry the same transient 269 MB buffer in both.
4. Allocator and allocation rate: both use the system allocator (glibc malloc in the gnu builds, musl malloc in the musl builds). The Rust decode path allocates a new Vec for nearly every intermediate (rmsnorm, matvec outputs, per-head scores, per-head output, rope scratch, KV cache entries as Vec<Vec<f32>> per position), thousands of allocations per generated token; the C path allocates 15 buffers per position plus one small scratch per head per layer for RoPE (about 360 per position) and keeps K and V in one contiguous array per layer. This is a property of the two source programs, left unchanged on purpose.
5. RoPE: Rust recomputes the pinned cos and sin for each head of each layer of each token (apply_rope_head); C computes them once per position. KV layout and attention loops differ.
6. Prefill: Rust computes the full logit vector at every prompt position; C at the last prompt position alone. Affects prefill wall, the warm-up prompt and total job time, not the timed window of decode steps 2 to 64.
7. Dot product: both are an indexed loop, one strict left-to-right add chain per output with no FMA (0 FMA instructions in all 8 binaries). Rust `dot_seq` is an #[inline] function in the same crate under fat LTO and indexes both slices (bounds checks stay unless LLVM removes them); C `cis2_dot_seq` and `cis2_matvec` live in a separate translation unit (mathpin.c, no LTO) and are called once per matrix-vector product.
8. Start-up work in time mode: Rust computes the inv_freq table digest (128 bytes through sha2) once at start; C does not. Outside every timed window; it is inside load_ns by a few microseconds.
9. Output: Rust prints with println (line buffered), C with printf and fflush after each prompt; after the timed window of each prompt in both.
10. Runner overhead, both arms equal in kind: the 50 ms smaps_rollup sampling (runner pinned away from the arm CPU where the host allows, R6) costs the runner process about 3.1 ms of CPU per sample for a 0.5 to 0.8 GB process on penguin (measured on a qemu process, a runner cost, not an arm timing); on the 1.1 to 2.1 GHz boxes it is larger, and on the single-core box4 it competes for the arm's single core (up to 10 to 20 percent of that core, ESTIMATE). It acts on both arms, but the bar asks for it and the runner records its CPU seconds per run (runner_cpu_s). The reading of the bar that applies the sampler during the timed run is kept to the letter.
11. Linkage: gnu builds are dynamic (PIE) against glibc 2.41; musl builds are static. The faster-of-two rule is applied per language per host over the builds that host ran, so musl-against-musl on box4 and box5, glibc-against-glibc on box1 to box3.
12. Compiler: Rust is rustc 1.98.0 / LLVM 22.1.8, C is gcc 14.2.0; same compiler effort means the two opt levels and the fixed flags written in the bar, nothing tuned afterwards.
