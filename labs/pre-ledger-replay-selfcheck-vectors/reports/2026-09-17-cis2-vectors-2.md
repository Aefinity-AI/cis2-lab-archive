## What was added

Two new op-level conformance vectors under `tests/conformance/vectors/`,
following `tests/conformance/PROTOCOL.md` exactly (the existing 5-vector
convention: `<name>.txt` + `<name>.expected`, generated from the
reference implementation, never hand-typed):

1. **softmax_v1** — spec §9.3 (`softmax_seq`: strict-sequential max-scan
   with first-occurrence-wins tie break, pinned-exp max-subtract §6.2,
   §5.3 sequential-sum denominator, elementwise divide). Exercises
   `softmax_seq` standalone (existing `attention_block_v1` only exercises
   it as one step of a larger pipeline with dot-product-derived scores).
   `n=6`, values `1.5,-0.5,0.5,1.5,-3.0,0.0` deliberately include an
   exact tie for the max at indices 0 and 3.
2. **embed_lookup_v1** — spec §2.5 (`model.embed_tokens.weight`
   `[vocab,hidden]` row-major layout), pinning the
   `start = token_id * hidden` lookup expression from `src/main.rs`'s
   `forward_step`. `vocab=4`, `hidden=6`, `token_ids=0,3,1` (bundles 3
   lookups, non-monotonic order + last valid row, to catch
   off-by-one/stride bugs).

## Generation commands (exact, recorded in PR + README + vector file headers)

```
cargo test --test conformance_softmax          # derives softmax_v1.expected
cargo test --test conformance_embed_lookup     # derives embed_lookup_v1.expected
```

Both derivation tests reimplement the reference math/logic by including
`src/math.rs` by path (softmax) or reproducing `src/main.rs`'s lookup
expression verbatim (embed_lookup — pure indexing, no float math to
share). New files: `tests/conformance_softmax.rs`,
`tests/conformance_embed_lookup.rs`.

## Dual verification (PROTOCOL.md runner against reference candidate)

Added `op_softmax` / `op_embed_lookup` to
`src/bin/cis2_conformance_reference_candidate.rs`, then ran the actual
stdin/stdout protocol checker:

```
cargo build --release --bin cis2-conformance --bin cis2_conformance_reference_candidate
./target/release/cis2-conformance ./target/release/cis2_conformance_reference_candidate
```

Output (tail):
```
PASS  attention_block_v1
PASS  embed_lookup_v1
PASS  exp_pinned_v1
PASS  matvec_v1
PASS  rmsnorm_v1
PASS  rope_v1
PASS  softmax_v1

all 7 vector(s) passed
```

Note: `PROTOCOL.md`/the repo has no separate standalone `cis2-verify`
binary distinct from `cis2-conformance` for op-level vectors — that
naming (`cis2-verify2`/`cis2-verify3`) refers to the full-model §13.1
clean-room witness-digest verifiers, which are out of scope for
op-level PROTOCOL.md vectors (documented explicitly in
`tests/conformance/PROTOCOL.md` "What this does NOT cover"). The dual
check actually used, matching the other 5 existing vectors' own
precedent, is: (1) the `cargo test --test conformance_<op>` derivation
test (independent reimplementation path) and (2) the
`cis2-conformance` CLI run against `cis2_conformance_reference_candidate`
(the protocol's own stdin/stdout wire contract), both shown above.

## CI

`.github/workflows/verify.yml`'s `conformance` job already discovers all
`tests/conformance/vectors/*.txt` files generically (dual-ISA
x86_64/aarch64, asserts `all N vector(s) passed`), so the two new
vectors were picked up automatically — no matrix-name changes were
possible or needed there. Added an explicit CI step running the two new
vectors' `cargo test` derivation self-checks on both ISAs
(`cargo test --release --test conformance_softmax --test conformance_embed_lookup`).

All CI jobs went green (cis2-verify, conformance, intermediates x20,
reference, verify2, verify3 — all `pass`, both x86_64 and aarch64) within
~2 minutes of pushing.
